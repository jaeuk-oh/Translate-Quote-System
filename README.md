## 1. 문제 정의 (Why)

번역 프로젝트에서 실제로 시간이 가장 많이 걸리는 곳은 어디인가?

번역 작업 자체가 아니다. **의사결정이 지연되는 구간**이다.

- 견적 산정: 담당자가 단어 수를 세고, 언어 조합을 확인하고, TM 매칭률을 수동으로 계산 — 수 시간 소요
- 번역가 배정: 누가 현재 여유 있는지, 품질 이력이 어떤지, 마감 준수율이 어떤지 — 담당자의 경험과 기억에 의존
- 상태 확인: 지금 어느 단계인지 알려면 직접 연락해야 함

결과적으로 **번역가는 기다리고, 클라이언트는 기다리고, 운영자는 중간에서 조율을 반복**한다.

## 2. 문제 재정의 (Reframing)

처음엔 이렇게 생각했다.

> "견적 계산을 자동화하면 되겠다."

그런데 파고들수록 더 근본적인 문제가 보였다.

> "번역 프로세스 전체가 사람의 판단을 매번 필요로 하는 구조로 설계되어 있다."

개별 단계의 자동화가 아니라, **흐름 자체를 재설계**해야 했다.

| 처음 생각한 문제 | 실제 문제 |
|-----------------|-----------|
| 견적 계산이 느리다 | 요청이 들어와도 다음 단계로 진행되려면 사람의 개입이 필요하다 |
| 배정이 비효율적이다 | 배정 기준이 명문화되지 않아 매번 새로운 판단이 필요하다 |
| 상태 확인이 불편하다 | 상태 자체가 시스템에 기록되지 않아 사람이 추적해야 한다 |

재정의한 문제:

> "번역 의뢰가 들어왔을 때, 운영자 없이도 다음 단계로 자동으로 흐를 수 있는가?"

이 질문이 이 시스템의 설계 원칙이 되었다.

## 3. 시스템 설계 (How I Designed)

### 전체 서비스 플로우

```
┌─────────────────────────────────────────────────────────────────┐
│  STAGE 1. 의뢰 접수                                             │
└─────────────────────────────────────────────────────────────────┘

고객 — /request 폼에서 의뢰 정보 입력
  (이름, 이메일, 언어쌍, 문서 유형, 품질 등급, 단어수, 마감일)
      │
      ▼
 [job 생성 — REQUESTED 상태]
  - job_id, 고객 정보, 언어 조합 저장
  - word_count가 있으면 즉시 Celery 견적 계산 큐 등록
 (Redis SETNX로 job_id 락 → 중복 enqueue 방지)


┌─────────────────────────────────────────────────────────────────┐
│  STAGE 2. 자동 견적 산정                                        │
└─────────────────────────────────────────────────────────────────┘

Celery 워커 픽업
      │
      ▼
 FSM: REQUESTED → QUOTE_PENDING
      │
      ▼
 [TM(Translation Memory) 매칭 — pg_trgm]
  - 동일 언어 조합 이력 세그먼트와 trigram 유사도 비교
  - TM 데이터 없으면 매칭률 0%로 처리 → 흐름 계속
      │
      ▼
 [할인율 결정]

  ┌─────────────────────────────────────┐
  │  TM 매칭률      →  할인율           │
  │  100%           →  100% (비용 = 0) │
  │  75% ~ 99%      →  70% 할인        │
  │  50% ~ 74%      →  40% 할인        │
  │  50% 미만       →  할인 없음        │
  └─────────────────────────────────────┘

      │
      ▼
 [최종 견적 계산]

  견적 = (단어 수 × 언어 단가) × (1 - 할인율) × 긴급 할증
                                                    ↑
                                   납기까지 24h 미만: ×1.5
                                   납기까지 48h 미만: ×1.2
                                   그 외: ×1.0
      │
      ▼
 FSM: QUOTE_PENDING → QUOTED_DRAFT
 담당자에게 "견적 검토 요청" 이메일 발송


┌─────────────────────────────────────────────────────────────────┐
│  STAGE 3. 담당자 견적 검토 → 고객 발송                         │
└─────────────────────────────────────────────────────────────────┘

담당자 — 관리자 대시보드에서 견적 내용 확인
      │
      ▼
 [고객에게 견적 발송]
  FSM: QUOTED_DRAFT → QUOTED
  고객에게 견적 이메일 발송 (승인/거절 링크 포함, JWT 토큰 7일 유효)


┌─────────────────────────────────────────────────────────────────┐
│  STAGE 4. 고객 견적 승인/거절                                   │
└─────────────────────────────────────────────────────────────────┘

고객 — 이메일 링크 클릭 (로그인 불필요, 토큰 인증)
      │
  ┌───┴──── 거절
  │                └──▶ FSM: QUOTED → CANCELLED
  │
  └──── 승인
              └──▶ FSM: QUOTED → ASSIGNED
                    Celery 번역가 자동 배정 큐 등록


┌─────────────────────────────────────────────────────────────────┐
│  STAGE 5. 번역가 자동 배정                                      │
└─────────────────────────────────────────────────────────────────┘

Celery 워커 픽업
      │
      ▼
 [후보 번역가 필터링]
  조건 1: 해당 언어 조합 가능
  조건 2: workload_ratio < 1.0 (현재 부하 최대치 미만)
      │
  ┌───┴──── 후보 0명
  │                └──▶ 1시간 후 재시도 (최대 3회)
  │                      모두 실패 → 관리자 Slack 에스컬레이션
  │
  ▼ 후보 존재
 [점수 산정 — 상위 3명 추출]

  score = (품질 점수   × 0.40)
        + (납기 준수율 × 0.30)
        + (가용성      × 0.20)
        + (부하 역수   × 0.10)

  ※ 신규 번역가 콜드 스타트: 품질/납기 이력 없음
     → 품질 점수 기본값 3.5/5.0, 납기 준수율 기본값 0.85 적용
      │
      ▼
 배정 레코드 생성 (ASSIGNED 상태 유지 — 담당자 확정 대기)


┌─────────────────────────────────────────────────────────────────┐
│  STAGE 6. 담당자 배정 확정                                      │
└─────────────────────────────────────────────────────────────────┘

담당자 — 대시보드에서 추천 번역가 목록 확인 후 확정
      │
      ▼
 FSM: ASSIGNED → IN_PROGRESS
 번역가에게 배정 확정 이메일 발송 (완료 파일 제출 링크 포함)


┌─────────────────────────────────────────────────────────────────┐
│  STAGE 7. 번역 작업 및 결과물 제출                              │
└─────────────────────────────────────────────────────────────────┘

번역가 — 이메일 링크를 통해 /submit/{job_id}?token=... 접속
      │
      ▼
 [완료 파일 업로드 — Supabase Storage]
  - 허용 포맷: docx, doc, pdf, txt, xlsx, pptx, xliff
  - JWT 제출 토큰 인증 (14일 유효, 로그인 불필요)
      │
      ▼
 FSM: IN_PROGRESS → REVIEW
 담당자에게 "검토 요청" 이메일 발송


┌─────────────────────────────────────────────────────────────────┐
│  STAGE 8. 검토 및 QA                                            │
└─────────────────────────────────────────────────────────────────┘

담당자 — 대시보드에서 완료 파일 다운로드 후 검토
      │
      ▼
 FSM: REVIEW → QA
      │
  ┌───┴──── QA 통과
  │                └──▶ FSM: QA → COMPLETED
  │                      고객에게 완료 알림 발송
  │
  └──── QA 실패
              └──▶ FSM: QA → IN_PROGRESS
                    번역가에게 재작업 요청 → STAGE 7 복귀


┌─────────────────────────────────────────────────────────────────┐
│  STAGE 9. 완료                                                  │
└─────────────────────────────────────────────────────────────────┘

FSM: COMPLETED 진입
고객에게 완료 알림 + 다운로드 링크 발송
```

### 상태 머신 전이도 (FSM)

```
REQUESTED
    │
    ▼ (Celery 견적 계산 큐 등록)
QUOTE_PENDING
    │
    ▼ (자동 견적 완료)
QUOTED_DRAFT ──▶ (담당자 검토 후 고객 발송)
    │
    ▼
QUOTED
    │
    ├──▶ 고객 거절 ──▶ CANCELLED
    │
    ▼ (고객 승인 → Celery 배정 큐 등록)
ASSIGNED ──▶ (담당자 배정 확정)
    │
    ▼
IN_PROGRESS ──▶ (번역가 완료 파일 제출)
    │
    ▼
REVIEW ──▶ (담당자 검토 → QA 이관)
    │
    ▼
QA
    │
    ├──▶ 통과 ──▶ COMPLETED
    │
    └──▶ 반려 ──▶ IN_PROGRESS (재작업)

어느 상태에서든: ──▶ CANCELLED (COMPLETED 제외)
```

### 예외 처리 전략 요약

| 구간 | 예외 상황 | 처리 방식 | 근거 |
|------|-----------|-----------|------|
| TM 매칭 | 이력 없음 | 매칭률 0%로 처리, 흐름 계속 | 신규 고객도 프로세스 진행 가능해야 함 |
| 번역가 배정 | 0명 적합자 | 1시간 후 재시도 (최대 3회) → Slack 에스컬레이션 | 자동화 실패 시 사람이 개입할 수 있는 출구 확보 |
| QA 실패 | 반려 | FSM: QA → IN_PROGRESS (번역가 재작업) | 무한 루프는 운영자가 수동 취소로 차단 |
| 알림 발송 | 모든 재시도 실패 | DLQ 적재, 상태 전이는 유지 | 알림 실패가 비즈니스 상태를 되돌리면 안 됨 |
| FSM 전이 | 허용되지 않은 전이 | FSMException + DB 롤백 | 상태 무결성 보장, 이력 오염 방지 |
| 중복 실행 | 워커 재시작/재시도 | Redis SETNX 멱등성 락 | 같은 job이 두 번 처리되는 경쟁 조건 방지 |

### Decision Points

```
번역가 배정 시점:
  후보 번역가 존재? ─── NO ──▶ 1시간 후 재시도 (최대 3회) → Slack 에스컬레이션

QA 검수 시점:
  통과? ─── NO ──▶ FSM: QA → IN_PROGRESS (재작업 요청)
              운영자가 수동으로 CANCELLED 처리 가능

알림 발송 시점:
  발송 성공? ─── NO ──▶ 지수 백오프 재시도 → DLQ (상태는 유지)
```

## 4. 자동화 접근 방식

### 사람이 하던 일을 어떻게 치환했는가

**견적 산정:** 담당자가 수작업으로 계산하던 것을 규칙 엔진으로 치환했다.

업계 표준 CAT(Computer-Assisted Translation) tool은 **글자 재사용률**로 할인율을 결정한다. 벡터 기반 의미 유사도가 아니라, 실제로 동일한 문자가 얼마나 재사용되는지가 기준이다. 이 방식을 PostgreSQL의 `pg_trgm` 확장으로 구현했다. 외부 AI API를 사용하지 않아 고객 문서의 NDA 위반 리스크도 없다.

```
100% 일치 → 무료
75~99%    → 70% 할인
50~74%    → 40% 할인
< 50%     → 할인 없음
```

**번역가 배정:** 담당자의 경험과 기억에 의존하던 것을 점수 모델로 명문화했다.

```
score = (품질 점수  × 0.40)
      + (납기 준수율 × 0.30)
      + (가용성      × 0.20)
      + (부하 역수   × 0.10)
```

가중치 설계 근거: 번역 품질이 클라이언트 신뢰의 핵심이므로 40%. 납기 미준수는 클라이언트 비즈니스에 직결되므로 30%. 나머지는 운영 효율 보조 지표.

**상태 추적:** 전화/이메일로 확인하던 것을 SSE 실시간 스트림으로 치환했다.

상태 전이가 발생하는 순간 `job_events` 테이블에 이력이 기록되고, 연결된 클라이언트에게 즉시 푸시된다. 운영자가 중간에서 상태를 전달할 필요가 없다.

## 5. 핵심 구현

### 왜 이 기술 조합인가

| 기술 | 역할 | 선택 이유 |
|------|------|-----------|
| FastAPI + Celery | 비동기 작업 분리 | 견적 계산·배정이 블로킹 없이 백그라운드에서 실행되어야 하므로 |
| PostgreSQL + pg_trgm | TM 매칭 | 글자 기반 유사도 측정이 필요하고, 외부 전송 없이 DB 내에서 처리 가능하므로 |
| Redis | 큐 + 중복 방지 락 | Celery 브로커와 `SETNX` 기반 멱등성 보장을 단일 인프라로 처리 |
| SSE | 실시간 상태 푸시 | 서버 → 클라이언트 단방향이므로 WebSocket보다 구현이 단순하고 프록시 친화적 |
| JWT + Refresh Token | 무상태 인증 | 수평 확장 시 세션 공유 문제 없음 |

### FSM 단일 진입점

모든 상태 전이는 `services/state_machine.py`의 `transition()` 함수만 통과한다. DB 트랜잭션 내에서 `job.status` 업데이트 + `job_events` 기록이 원자적으로 처리된다. 허용되지 않은 전이는 `FSMException`으로 즉시 차단되고 롤백된다.

`SELECT FOR UPDATE` 행 잠금으로 동시에 두 워커가 같은 job을 전이시키는 경쟁 조건을 차단한다.

### Celery 워커와 Redis 큐

**워커란?**
FastAPI(웹 서버)와 분리된 별도 프로세스다. 웹 서버는 요청을 받으면 "견적 계산해줘"를 Redis 큐에 등록하고 즉시 응답을 돌려준다. 워커는 Redis 큐를 계속 바라보다가 항목이 생기면 꺼내서 실행한다.

```
고객 요청 → FastAPI → Redis 큐에 등록 → 즉시 응답
                              ↓
                       Celery 워커 (별도 프로세스)
                         견적 계산 / 배정 / 알림 실행
```

워커는 직접 작성한 코드이고, 프로세스 관리(재시도, 큐에서 꺼내기 등)는 Celery 라이브러리가 담당한다.

**FastAPI `BackgroundTasks` 대신 Celery를 쓴 이유**

두 가지 상황을 대비한 것이다.

_1. 서버 재시작 시 작업 유실_

고객이 견적 요청 → 견적 계산 중 서버가 재시작되면?
- BackgroundTasks: 태스크 사라짐. job이 `QUOTE_PENDING`에 영구히 묶임.
- Celery: 태스크가 Redis에 저장돼 있어서 워커 재시작 후 다시 처리.

_2. 외부 서비스 일시 장애_

이메일 발송 중 Resend API가 타임아웃되면?
- BackgroundTasks: 실패하고 끝. 번역가가 이메일을 못 받음.
- Celery: 실패 감지 → 1분 후 재시도 → 5분 후 재시도 → 15분 후 재시도 → 모두 실패 시 DLQ 적재.

**DLQ (Dead Letter Queue)**

재시도를 모두 소진해도 실패한 태스크를 버리지 않고 별도 큐에 보관한다. 사라지지 않기 때문에 나중에 원인 파악 후 수동 재실행하거나, 관리자가 Slack 알림으로 인지하고 대응할 수 있다. DLQ가 없으면 어떤 태스크가 왜 실패했는지 알 방법이 없다.

**멱등성과 Redis SETNX**

Celery는 태스크를 "이어서" 처리하는 게 아니라 **처음부터 다시** 실행한다. 따라서 같은 태스크가 두 번 실행돼도 결과가 동일해야 한다(멱등성). 이를 보장하기 위해 Redis `SETNX`로 job별 락을 걸어 중복 실행을 차단한다.

이 프로젝트의 워커는 3개다:
- `quote_worker` — 견적 자동 계산
- `assign_worker` — 번역가 자동 배정
- `notify_worker` — 이메일/Slack 알림 발송

## 7. 한계 & 개선 방향

### 아직 해결하지 못한 문제

**견적 승인은 여전히 사람이 한다.** 가격과 납기를 클라이언트가 판단해야 하므로, 이 구간은 자동화할 수 없다. 다만 견적 근거(TM 매칭률, 단가 계산 내역)를 투명하게 제공해 결정 속도를 높이는 방향으로 보완할 수 있다.

**QA 판단은 사람이 한다.** 번역 품질 검수는 자동화 기준을 정의하기 어렵다. 현재는 QA 단계에서 리뷰어가 수동으로 승인/반려한다. 장기적으로는 용어집 일치율, 번역 누락 감지 등 보조 지표를 자동 체크할 수 있다.

**배정 점수 모델은 초기값에 의존한다.** 품질 점수와 납기 준수율이 없는 신규 번역가는 점수가 낮게 계산된다. 콜드 스타트 문제를 완화하는 초기값 설정 전략이 필요하다.

## 8. 내가 얻은 인사이트

이 프로젝트를 통해 가장 크게 바뀐 생각:

> "자동화는 기능을 추가하는 것이 아니라, 의사결정을 명문화하는 것이다."

견적 계산 자동화는 수식 하나가 아니다. "TM 매칭률에 따라 얼마나 할인할 것인가"라는 **업계 표준을 코드로 선언**하는 것이다.

번역가 배정 자동화는 알고리즘 하나가 아니다. "어떤 번역가에게 어떤 기준으로 일을 줄 것인가"라는 **조직의 암묵지를 점수 모델로 형식화**하는 것이다.

**AI는 기능이 아니라 흐름에서 가치가 나온다.** 각 단계에서 잘 작동하는 컴포넌트보다, 단계들이 끊김 없이 연결되는 구조가 더 중요하다. 사람이 중간에서 조율하지 않아도 되는 흐름을 설계하는 것 — 그것이 이 시스템의 목표였다.

## 9. 확장 가능성

이 시스템의 핵심 구조는 **"요청 → 자동 분해 → 규칙 기반 처리 → 상태 추적 → 자동 알림"** 이다.

번역 플랫폼 외에도 동일한 구조가 적용되는 영역:

| 도메인 | 자동화 가능한 흐름 |
|--------|-------------------|
| 법률 문서 검토 | 접수 → 유형 분류 → 담당 변호사 배정 → 진행 상태 추적 |
| 디자인 외주 | 의뢰 → 작업 범위 산정 → 프리랜서 매칭 → 납품 |
| 고객 지원 티켓 | 접수 → 카테고리 분류 → 담당자 배정 → 에스컬레이션 |

변하는 것: 도메인 규칙(견적 공식, 배정 기준)
변하지 않는 것: FSM 기반 상태 관리, 비동기 워커, 이벤트 기반 알림 구조

이 설계를 범용 "작업 자동화 프레임워크"로 추상화하면, 도메인만 교체해 다른 워크플로우에 재사용할 수 있다.

## 10. 빠른 시작

### 환경 변수 설정

```bash
cp .env.example .env
# .env 파일을 열어 실제 값 입력
```

**Supabase DB 연결 주의사항**

Supabase free tier는 direct connection(`db.{ref}.supabase.co:5432`)이 IPv4를 지원하지 않는다. IPv4는 유료 플랜 전용이다.

따라서 free tier에서는 **Transaction Pooler URL**을 `DATABASE_URL`에 직접 입력해야 한다:

```env
DATABASE_URL=postgresql+asyncpg://postgres.{ref}:{password}@{pooler-host}:6543/postgres
```

pooler host와 전체 connection string은 Supabase 대시보드 → **Settings → Database → Connection string → URI** 탭에서 확인. `postgresql://` 앞부분을 `postgresql+asyncpg://`로 바꿔서 사용한다.

### DB 초기화 (Supabase)

Supabase 대시보드 → SQL Editor에서 `apps/api/db/schema.sql` 실행.

### 백엔드 실행

```bash
cd apps/api
pip install -r requirements.txt
uvicorn main:app --reload --port 8000
```

### Celery 워커 실행

```bash
cd apps/api
celery -A workers.celery_app worker --loglevel=info
```

### 프론트엔드 실행

```bash
cd apps/web
npm install
npm run dev
```

### API 문서 확인

- Swagger UI: `http://localhost:8000/docs`
- ReDoc: `http://localhost:8000/redoc`
