## 1. 문제 정의 (Why)

번역 프로젝트에서 실제로 시간이 가장 많이 걸리는 곳은 어디인가?

번역 작업 자체가 아니다. **의사결정이 지연되는 구간**이다.

- 견적 산정: 담당자가 단어 수를 세고, 언어 조합을 확인하고, TM 매칭률을 수동으로 계산 — 수 시간 소요
- 번역가 배정: 누가 현재 여유 있는지, 품질 이력이 어떤지, 마감 준수율이 어떤지 — 담당자의 경험과 기억에 의존
- 상태 확인: 지금 어느 단계인지 알려면 직접 연락해야 함

결과적으로 **번역가는 기다리고, 클라이언트는 기다리고, 운영자는 중간에서 조율을 반복**한다.

## 2. 문제 재정의 (Reframing)

처음엔 이렇게 생각했다.

> "견적 계산을 자동화하면 되겠다."

그런데 파고들수록 더 근본적인 문제가 보였다.

> "번역 프로세스 전체가 사람의 판단을 매번 필요로 하는 구조로 설계되어 있다."

개별 단계의 자동화가 아니라, **흐름 자체를 재설계**해야 했다.

| 처음 생각한 문제 | 실제 문제 |
|-----------------|-----------|
| 견적 계산이 느리다 | 요청이 들어와도 다음 단계로 진행되려면 사람의 개입이 필요하다 |
| 배정이 비효율적이다 | 배정 기준이 명문화되지 않아 매번 새로운 판단이 필요하다 |
| 상태 확인이 불편하다 | 상태 자체가 시스템에 기록되지 않아 사람이 추적해야 한다 |

재정의한 문제:

> "번역 의뢰가 들어왔을 때, 운영자 없이도 다음 단계로 자동으로 흐를 수 있는가?"

이 질문이 이 시스템의 설계 원칙이 되었다.

## 3. 시스템 설계 (How I Designed)

### 전체 서비스 플로우 (예외 경로 포함)

정상 경로(happy path)만 그리는 것은 설계가 아니다. 각 단계에서 무엇이 실패할 수 있고, 그때 시스템이 어떻게 반응하는지가 설계의 본질이다.

```
┌─────────────────────────────────────────────────────────────────┐
│  STAGE 1. 의뢰 접수 및 유효성 검증                              │
└─────────────────────────────────────────────────────────────────┘

클라이언트 요청
      │
      ▼
 [입력 검증]
  - 언어 조합 지원 여부
  - 파일 형식 허용 여부 (PDF, DOCX, TXT ...)
  - 파일 크기 제한 (50MB)
  - 납기 최소 요건 (언어 조합별 최소 1~3일)
      │
  ┌───┴──── 검증 실패
  │                └──▶ 400 Bad Request + 거절 사유 반환 → 종료
  │
  ▼ 검증 통과
 [파일 S3 업로드]
      │
  ┌───┴──── 업로드 실패 (네트워크/스토리지 오류)
  │                └──▶ 최대 3회 재시도 (지수 백오프: 1s → 2s → 4s)
  │                      재시도 모두 실패 → 500 반환, job 생성 안 함
  │
  ▼ 업로드 완료
 [job 생성 — REQUESTED 상태]
  - job_id, 파일 메타데이터, 언어 조합 저장
  - 클라이언트에게 job_id 반환 (이후 SSE 구독 가능)
      │
      ▼
 Celery 태스크 큐에 "견적 계산" 작업 enqueue
 (Redis SETNX로 job_id 락 → 중복 enqueue 방지)


┌─────────────────────────────────────────────────────────────────┐
│  STAGE 2. 자동 견적 산정                                        │
└─────────────────────────────────────────────────────────────────┘

Celery 워커 픽업
      │
      ▼
 FSM: REQUESTED → QUOTE_PENDING
      │
      ▼
 [단어 수 추출]
  - 파일 포맷별 파서 (DOCX → python-docx, PDF → pdfplumber)
      │
  ┌───┴──── 파싱 실패 (손상된 파일, 암호화된 PDF 등)
  │                └──▶ FAILED 상태 전이 + 클라이언트 알림
  │                      "파일을 읽을 수 없습니다. 다시 업로드해주세요."
  │
  ▼ 파싱 성공
 [TM(Translation Memory) 매칭 — pg_trgm]
  - 동일 클라이언트 + 동일 언어 조합 이력 세그먼트와 비교
  - trigram 유사도 점수 계산
      │
  ┌───┴──── TM 데이터 없음 (신규 클라이언트 or 신규 언어 조합)
  │                └──▶ 매칭률 0%로 간주 → 할인 없음으로 계속
  │
  ▼
 [할인율 결정]

  ┌─────────────────────────────────────┐
  │  TM 매칭률      →  할인율           │
  │  100%           →  100% (비용 = 0) │
  │  75% ~ 99%      →  70% 할인        │
  │  50% ~ 74%      →  40% 할인        │
  │  50% 미만       →  할인 없음        │
  └─────────────────────────────────────┘

      │
      ▼
 [최종 견적 계산]

  견적 = (단어 수 × 언어 단가) × (1 - 할인율) × 긴급 할증
                                                    ↑
                                   납기까지 24h 미만: ×1.5
                                   납기까지 48h 미만: ×1.2
                                   그 외: ×1.0
      │
      ▼
 [특수 케이스 처리]

  TM 100% 전체 일치?
  ├── YES → 비용 = 0 → 견적 승인 단계 스킵
  │          FSM: QUOTE_PENDING → PENDING_ACC (자동 승인)
  │          → STAGE 3으로 바로 진행
  │
  └── NO  → FSM: QUOTE_PENDING → QUOTED
             클라이언트 이메일 발송 (견적서 + TM 근거 내역)
             48시간 타임아웃 타이머 시작


┌─────────────────────────────────────────────────────────────────┐
│  STAGE 3. 견적 승인 대기 (유일한 수동 개입 구간)                │
└─────────────────────────────────────────────────────────────────┘

클라이언트 응답 대기
      │
  ┌───┼──── 48시간 초과 응답 없음
  │   │            └──▶ FSM: QUOTED → EXPIRED
  │   │                  운영자 알림 + 클라이언트 리마인드 이메일 1회 발송
  │   │                  추가 24시간 후 응답 없으면 → CANCELLED
  │   │
  │   ├──── 클라이언트 거절
  │   │            └──▶ FSM: QUOTED → CANCELLED
  │   │                  거절 사유 기록 (job_events 이력)
  │   │
  │   └──── 클라이언트 승인
  │                └──▶ FSM: QUOTED → PENDING_ACC
  │
  ▼ PENDING_ACC 진입
 Celery 태스크 큐에 "번역가 배정" 작업 enqueue


┌─────────────────────────────────────────────────────────────────┐
│  STAGE 4. 번역가 자동 배정                                      │
└─────────────────────────────────────────────────────────────────┘

Celery 워커 픽업
      │
      ▼
 [후보 번역가 필터링]
  조건 1: 해당 언어 조합 가능
  조건 2: 해당 전문 분야 보유
  조건 3: workload_ratio < 1.0 (현재 부하가 최대치 미만)
  조건 4: 납기 내 완료 가능한 가용 시간 보유
      │
  ┌───┴──── 후보 0명
  │                └──▶ 필터 조건 단계적 완화 후 재탐색
  │                      1차: 전문 분야 조건 완화 (근접 분야 허용)
  │                      2차: workload_ratio < 1.2로 완화
  │                      그래도 0명 → FSM: PENDING_ACC → NO_TRANSLATOR
  │                                    운영자 에스컬레이션 알림
  │
  ▼ 후보 존재
 [점수 산정 — 상위 3명 추출]

  score = (품질 점수   × 0.40)
        + (납기 준수율 × 0.30)
        + (가용성      × 0.20)
        + (부하 역수   × 0.10)

  ※ 신규 번역가 콜드 스타트: 품질/납기 이력 없음
     → 품질 점수 기본값 3.5/5.0, 납기 준수율 기본값 0.85 적용
      │
      ▼
 [1순위 번역가에게 배정 요청 발송]
  FSM: PENDING_ACC → ASSIGNED (낙관적 전이)
  이메일 + 대시보드 알림 발송
  24시간 응답 타임아웃 타이머 시작
      │
  ┌───┴──── 알림 발송 실패
  │                └──▶ 지수 백오프 재시도 (1m → 5m → 15m, 최대 3회)
  │                      모두 실패 → DLQ 적재 + 운영자 알림
  │
  ┌───┴──── 번역가 거절 또는 24시간 미응답
  │                └──▶ FSM: ASSIGNED → REASSIGNING
  │                      거절 사유 기록 (job_events)
  │                      2순위 번역가에게 동일 프로세스 반복
  │                      3순위까지 모두 거절 → NO_TRANSLATOR 에스컬레이션
  │
  ▼ 번역가 수락
 FSM: ASSIGNED → IN_PROGRESS
 클라이언트에게 "배정 완료 + 담당 번역가 정보" 알림


┌─────────────────────────────────────────────────────────────────┐
│  STAGE 5. 작업 진행 및 상태 추적                                │
└─────────────────────────────────────────────────────────────────┘

번역가 작업 중 — SSE 실시간 스트림 연결 유지
      │
  ┌───┴──── 번역가 중도 포기 (포기 신청 또는 응답 두절)
  │                └──▶ FSM: IN_PROGRESS → REASSIGNING
  │                      납기까지 남은 시간 재계산
  │                      긴급도 상향 후 새 후보 탐색 → STAGE 4 재진입
  │                      (납기 48h 미만이면 운영자 즉시 알림)
  │
  ├───┴──── 납기 초과 감지 (Celery beat 주기 체크)
  │                └──▶ 번역가 + 운영자 경고 알림 발송
  │                      (자동으로 배정 취소하지 않음 — 강제 취소보다
  │                       상황 파악 후 판단이 더 안전하다고 설계 결정)
  │
  ▼ 번역가 납품 완료 (파일 S3 업로드)
 FSM: IN_PROGRESS → REVIEW
 클라이언트 + QA 담당자에게 검수 요청 알림


┌─────────────────────────────────────────────────────────────────┐
│  STAGE 6. QA 검수                                               │
└─────────────────────────────────────────────────────────────────┘

QA 담당자 검수 진행
      │
  ┌───┴──── QA 통과
  │                └──▶ FSM: REVIEW → COMPLETED
  │                      → STAGE 7 (완료 처리)
  │
  └───┴──── QA 실패 (번역 오류, 누락, 용어 불일치 등)
                   └──▶ 실패 사유 기록 (job_events)
                         retry_count += 1

                         retry_count ≤ 3?
                         ├── YES → FSM: REVIEW → IN_PROGRESS
                         │          번역가에게 재작업 요청 + 실패 사유 전달
                         │          → STAGE 5로 복귀
                         │
                         └── NO  → FSM: REVIEW → ESCALATED
                                    운영자 에스컬레이션
                                    수동 처리 (환불/재배정/협의)


┌─────────────────────────────────────────────────────────────────┐
│  STAGE 7. 완료 처리 및 알림                                     │
└─────────────────────────────────────────────────────────────────┘

FSM: COMPLETED 진입
      │
      ▼
 병렬 처리 (Celery group):
  ├── 클라이언트 완료 알림 + 다운로드 링크 발송
  ├── 번역가 정산 정보 기록 (작업량, 단가, 총액)
  ├── TM 업데이트 (번역 결과를 TM DB에 적재 — 다음 의뢰 시 매칭 활용)
  └── 번역가 품질 점수 갱신 (QA 결과 반영)
      │
  ┌───┴──── 알림 발송 실패
  │                └──▶ 지수 백오프 재시도
  │                      모두 실패 → DLQ 적재
  │                      (완료 상태는 이미 확정 — 알림 실패가 완료 자체를 되돌리지 않음)
  │
  ▼ 모든 후처리 완료
 job 종결
```

### 상태 머신 전이도 (FSM)

```
                        파싱 실패
REQUESTED ──▶ QUOTE_PENDING ──────────────────────▶ FAILED
                    │
              견적 계산 완료
                    │
              TM 100% 전체 일치?
              ├── YES ──────────────────────────────┐
              │                                     │
              └── NO ──▶ QUOTED                     │
                           │                        │
                      48h 경과                      │
                      응답 없음 ──▶ EXPIRED          │
                           │         │              │
                      클라이언트    추가 24h         │
                        거절        경과             │
                           │         │              │
                           ▼         ▼              ▼
                       CANCELLED  CANCELLED    PENDING_ACC
                                                    │
                                              번역가 배정
                                                    │
                                               ASSIGNED
                                              ╱         ╲
                                    번역가 거절/미응답   번역가 수락
                                           ↓                ↓
                                     REASSIGNING      IN_PROGRESS
                                     (재탐색 후            │
                                      ASSIGNED로)     납품 완료
                                           │              │
                                    3회 모두 거절        REVIEW
                                           ↓          ╱       ╲
                                    NO_TRANSLATOR  QA 실패   QA 통과
                                    (에스컬레이션)    ↓           ↓
                                                IN_PROGRESS  COMPLETED
                                                (retry ≤ 3)
                                                재시도 초과 →
                                                 ESCALATED
```

### 예외 처리 전략 요약

| 구간 | 예외 상황 | 처리 방식 | 근거 |
|------|-----------|-----------|------|
| 파일 업로드 | 네트워크/스토리지 오류 | 지수 백오프 3회 재시도, 실패 시 job 미생성 | 불완전한 job보다 깔끔한 실패가 낫다 |
| 파일 파싱 | 손상/암호화 파일 | FAILED 상태 + 재업로드 안내 | 파싱 불가 파일로 견적 계산 불가 |
| TM 매칭 | 이력 없음 | 매칭률 0%로 처리, 흐름 계속 | 신규 클라이언트도 프로세스 진행 가능해야 함 |
| 견적 승인 | 48h 미응답 | 리마인드 1회 → 추가 24h → CANCELLED | 무한 대기 방지, 리소스 잠금 해제 |
| 번역가 배정 | 0명 적합자 | 필터 단계적 완화 → 실패 시 에스컬레이션 | 자동화 실패 시 사람이 개입할 수 있는 출구 확보 |
| 배정 응답 | 24h 미응답 | 다음 순위로 자동 재배정 | 번역가 무응답이 전체 흐름을 막지 않도록 |
| 작업 중 이탈 | 번역가 중도 포기 | 긴급도 상향 후 재배정 → STAGE 4 재진입 | 납기 영향 최소화 |
| 납기 초과 | Celery beat 감지 | 경고 알림만, 자동 취소하지 않음 | 강제 취소가 오히려 더 큰 피해 유발 가능 |
| QA 실패 | 3회 초과 | 운영자 에스컬레이션 | 무한 루프 방지, 수동 판단 개입 |
| 알림 발송 | 모든 재시도 실패 | DLQ 적재, 상태 전이는 유지 | 알림 실패가 비즈니스 상태를 되돌리면 안 됨 |
| FSM 전이 | 허용되지 않은 전이 | FSMException + DB 롤백 | 상태 무결성 보장, 이력 오염 방지 |
| 중복 실행 | 워커 재시작/재시도 | Redis SETNX 멱등성 락 | 같은 job이 두 번 처리되는 경쟁 조건 방지 |

---

### Decision Points

```
견적 계산 완료 시점:
  TM 100% 전체 일치? ─── YES ──▶ 비용 = 0, 견적 승인 단계 스킵
                    └── NO  ──▶ 클라이언트 견적 승인 대기

번역가 배정 시점:
  후보 번역가 존재? ─── NO ──▶ 필터 완화 재탐색 → 없으면 에스컬레이션
  배정 수락 응답?   ─── NO ──▶ 24h 후 다음 순위로 재배정 (최대 3순위)

QA 검수 시점:
  통과?          ─── NO ──▶ retry_count 확인
  retry ≤ 3?    ─── NO ──▶ 운영자 에스컬레이션 (자동화 한계 인정)

알림 발송 시점:
  발송 성공?     ─── NO ──▶ 지수 백오프 재시도 → DLQ (상태는 유지)
```

## 4. 자동화 접근 방식

### 사람이 하던 일을 어떻게 치환했는가

**견적 산정:** 담당자가 수작업으로 계산하던 것을 규칙 엔진으로 치환했다.

업계 표준 CAT(Computer-Assisted Translation) tool은 **글자 재사용률**로 할인율을 결정한다. 벡터 기반 의미 유사도가 아니라, 실제로 동일한 문자가 얼마나 재사용되는지가 기준이다. 이 방식을 PostgreSQL의 `pg_trgm` 확장으로 구현했다. 외부 AI API를 사용하지 않아 고객 문서의 NDA 위반 리스크도 없다.

```
100% 일치 → 무료
75~99%    → 70% 할인
50~74%    → 40% 할인
< 50%     → 할인 없음
```

**번역가 배정:** 담당자의 경험과 기억에 의존하던 것을 점수 모델로 명문화했다.

```
score = (품질 점수  × 0.40)
      + (납기 준수율 × 0.30)
      + (가용성      × 0.20)
      + (부하 역수   × 0.10)
```

가중치 설계 근거: 번역 품질이 클라이언트 신뢰의 핵심이므로 40%. 납기 미준수는 클라이언트 비즈니스에 직결되므로 30%. 나머지는 운영 효율 보조 지표.

**상태 추적:** 전화/이메일로 확인하던 것을 SSE 실시간 스트림으로 치환했다.

상태 전이가 발생하는 순간 `job_events` 테이블에 이력이 기록되고, 연결된 클라이언트에게 즉시 푸시된다. 운영자가 중간에서 상태를 전달할 필요가 없다.

## 5. 핵심 구현

### 왜 이 기술 조합인가

| 기술 | 역할 | 선택 이유 |
|------|------|-----------|
| FastAPI + Celery | 비동기 작업 분리 | 견적 계산·배정이 블로킹 없이 백그라운드에서 실행되어야 하므로 |
| PostgreSQL + pg_trgm | TM 매칭 | 글자 기반 유사도 측정이 필요하고, 외부 전송 없이 DB 내에서 처리 가능하므로 |
| Redis | 큐 + 중복 방지 락 | Celery 브로커와 `SETNX` 기반 멱등성 보장을 단일 인프라로 처리 |
| SSE | 실시간 상태 푸시 | 서버 → 클라이언트 단방향이므로 WebSocket보다 구현이 단순하고 프록시 친화적 |
| JWT + Refresh Token | 무상태 인증 | 수평 확장 시 세션 공유 문제 없음 |

### FSM 단일 진입점

모든 상태 전이는 `services/state_machine.py`의 `transition()` 함수만 통과한다. DB 트랜잭션 내에서 `job.status` 업데이트 + `job_events` 기록이 원자적으로 처리된다. 허용되지 않은 전이는 `FSMException`으로 즉시 차단되고 롤백된다.

`SELECT FOR UPDATE` 행 잠금으로 동시에 두 워커가 같은 job을 전이시키는 경쟁 조건을 차단한다.

## 7. 한계 & 개선 방향

### 아직 해결하지 못한 문제

**견적 승인은 여전히 사람이 한다.** 가격과 납기를 클라이언트가 판단해야 하므로, 이 구간은 자동화할 수 없다. 다만 견적 근거(TM 매칭률, 단가 계산 내역)를 투명하게 제공해 결정 속도를 높이는 방향으로 보완할 수 있다.

**QA 판단은 사람이 한다.** 번역 품질 검수는 자동화 기준을 정의하기 어렵다. 현재는 QA 단계에서 리뷰어가 수동으로 승인/반려한다. 장기적으로는 용어집 일치율, 번역 누락 감지 등 보조 지표를 자동 체크할 수 있다.

**배정 점수 모델은 초기값에 의존한다.** 품질 점수와 납기 준수율이 없는 신규 번역가는 점수가 낮게 계산된다. 콜드 스타트 문제를 완화하는 초기값 설정 전략이 필요하다.

## 8. 내가 얻은 인사이트

이 프로젝트를 통해 가장 크게 바뀐 생각:

> "자동화는 기능을 추가하는 것이 아니라, 의사결정을 명문화하는 것이다."

견적 계산 자동화는 수식 하나가 아니다. "TM 매칭률에 따라 얼마나 할인할 것인가"라는 **업계 표준을 코드로 선언**하는 것이다.

번역가 배정 자동화는 알고리즘 하나가 아니다. "어떤 번역가에게 어떤 기준으로 일을 줄 것인가"라는 **조직의 암묵지를 점수 모델로 형식화**하는 것이다.

**AI는 기능이 아니라 흐름에서 가치가 나온다.** 각 단계에서 잘 작동하는 컴포넌트보다, 단계들이 끊김 없이 연결되는 구조가 더 중요하다. 사람이 중간에서 조율하지 않아도 되는 흐름을 설계하는 것 — 그것이 이 시스템의 목표였다.

## 9. 확장 가능성

이 시스템의 핵심 구조는 **"요청 → 자동 분해 → 규칙 기반 처리 → 상태 추적 → 자동 알림"** 이다.

번역 플랫폼 외에도 동일한 구조가 적용되는 영역:

| 도메인 | 자동화 가능한 흐름 |
|--------|-------------------|
| 법률 문서 검토 | 접수 → 유형 분류 → 담당 변호사 배정 → 진행 상태 추적 |
| 디자인 외주 | 의뢰 → 작업 범위 산정 → 프리랜서 매칭 → 납품 |
| 고객 지원 티켓 | 접수 → 카테고리 분류 → 담당자 배정 → 에스컬레이션 |

변하는 것: 도메인 규칙(견적 공식, 배정 기준)
변하지 않는 것: FSM 기반 상태 관리, 비동기 워커, 이벤트 기반 알림 구조

이 설계를 범용 "작업 자동화 프레임워크"로 추상화하면, 도메인만 교체해 다른 워크플로우에 재사용할 수 있다.
