## 1. 문제 정의 (Why)

번역 프로젝트에서 실제로 시간이 가장 많이 걸리는 곳은 어디인가?

번역 작업 자체가 아니다. **의사결정이 지연되는 구간**이다.

- 견적 산정: 담당자가 단어 수를 세고, 언어 조합을 확인하고, TM 매칭률을 수동으로 계산 — 수 시간 소요
- 번역가 배정: 누가 현재 여유 있는지, 품질 이력이 어떤지, 마감 준수율이 어떤지 — 담당자의 경험과 기억에 의존
- 상태 확인: 지금 어느 단계인지 알려면 직접 연락해야 함

결과적으로 **번역가는 기다리고, 클라이언트는 기다리고, 운영자는 중간에서 조율을 반복**한다.

## 2. 문제 재정의 (Reframing)

처음엔 이렇게 생각했다.

> "견적 계산을 자동화하면 되겠다."

그런데 파고들수록 더 근본적인 문제가 보였다.

> "번역 프로세스 전체가 사람의 판단을 매번 필요로 하는 구조로 설계되어 있다."

개별 단계의 자동화가 아니라, **흐름 자체를 재설계**해야 했다.

| 처음 생각한 문제 | 실제 문제 |
|-----------------|-----------|
| 견적 계산이 느리다 | 요청이 들어와도 다음 단계로 진행되려면 사람의 개입이 필요하다 |
| 배정이 비효율적이다 | 배정 기준이 명문화되지 않아 매번 새로운 판단이 필요하다 |
| 상태 확인이 불편하다 | 상태 자체가 시스템에 기록되지 않아 사람이 추적해야 한다 |

재정의한 문제:

> "번역 의뢰가 들어왔을 때, 운영자 없이도 다음 단계로 자동으로 흐를 수 있는가?"

이 질문이 이 시스템의 설계 원칙이 되었다.

## 3. 시스템 설계 (How I Designed)

### 전체 워크플로우

```
[번역 의뢰 등록]
      │
      ▼
[요청 분해]  ← 언어 조합, 분량, 납기, 전문 분야
      │
      ▼
[자동 견적 산정]  ← TM 매칭률 × 단가 + 언어 가중치 + 긴급 할증
      │
      ▼
[견적 승인 대기]  ← 클라이언트 결정 필요 (유일한 사람 개입 구간)
      │
      ▼
[번역가 자동 배정]  ← 점수 기반 랭킹, 가용성 필터링
      │
      ▼
[작업 진행 + 상태 추적]  ← FSM이 상태 전이를 관리
      │
      ▼
[완료 감지 + 알림]  ← 이벤트 기반 자동 발송
```

### 상태 흐름 (FSM)

```
REQUESTED
    │
    ▼
QUOTE_PENDING ──(자동 계산 완료)──▶ QUOTED
                                        │
                                   승인/거절
                                   ┌────┴────┐
                                   ▼         ▼
                           PENDING_ACC   CANCELLED
                                   │
                                   ▼
                               ASSIGNED
                                   │
                                   ▼
                             IN_PROGRESS
                                   │
                              납품 완료
                                   ▼
                                REVIEW
                                   │
                              QA 통과/실패
                               ┌───┴───┐
                               ▼       ▼
                           COMPLETED  IN_PROGRESS
                                      (최대 3회)
```

### Decision Points

각 단계는 조건에 따라 자동으로 분기한다.

| 구간 | 조건 | 자동 처리 |
|------|------|-----------|
| 견적 계산 | TM 매칭률 ≥ 100% | 비용 = 0, 즉시 승인 진행 |
| 번역가 배정 | workload_ratio ≥ 1.0 | 자동 제외, 다음 순위로 |
| 배정 응답 | 24시간 미응답 | EXPIRED → 2순위 자동 재배정 |
| QA 실패 | 재시도 3회 초과 | 관리자 에스컬레이션 |
| 알림 실패 | 지수 백오프 재시도 실패 | DLQ 보관, 알림 후 처리 |

## 4. 자동화 접근 방식

### 사람이 하던 일을 어떻게 치환했는가

**견적 산정:** 담당자가 수작업으로 계산하던 것을 규칙 엔진으로 치환했다.

업계 표준 CAT(Computer-Assisted Translation) tool은 **글자 재사용률**로 할인율을 결정한다. 벡터 기반 의미 유사도가 아니라, 실제로 동일한 문자가 얼마나 재사용되는지가 기준이다. 이 방식을 PostgreSQL의 `pg_trgm` 확장으로 구현했다. 외부 AI API를 사용하지 않아 고객 문서의 NDA 위반 리스크도 없다.

```
100% 일치 → 무료
75~99%    → 70% 할인
50~74%    → 40% 할인
< 50%     → 할인 없음
```

**번역가 배정:** 담당자의 경험과 기억에 의존하던 것을 점수 모델로 명문화했다.

```
score = (품질 점수  × 0.40)
      + (납기 준수율 × 0.30)
      + (가용성      × 0.20)
      + (부하 역수   × 0.10)
```

가중치 설계 근거: 번역 품질이 클라이언트 신뢰의 핵심이므로 40%. 납기 미준수는 클라이언트 비즈니스에 직결되므로 30%. 나머지는 운영 효율 보조 지표.

**상태 추적:** 전화/이메일로 확인하던 것을 SSE 실시간 스트림으로 치환했다.

상태 전이가 발생하는 순간 `job_events` 테이블에 이력이 기록되고, 연결된 클라이언트에게 즉시 푸시된다. 운영자가 중간에서 상태를 전달할 필요가 없다.

## 5. 핵심 구현

### 왜 이 기술 조합인가

| 기술 | 역할 | 선택 이유 |
|------|------|-----------|
| FastAPI + Celery | 비동기 작업 분리 | 견적 계산·배정이 블로킹 없이 백그라운드에서 실행되어야 하므로 |
| PostgreSQL + pg_trgm | TM 매칭 | 글자 기반 유사도 측정이 필요하고, 외부 전송 없이 DB 내에서 처리 가능하므로 |
| Redis | 큐 + 중복 방지 락 | Celery 브로커와 `SETNX` 기반 멱등성 보장을 단일 인프라로 처리 |
| SSE | 실시간 상태 푸시 | 서버 → 클라이언트 단방향이므로 WebSocket보다 구현이 단순하고 프록시 친화적 |
| JWT + Refresh Token | 무상태 인증 | 수평 확장 시 세션 공유 문제 없음 |

### FSM 단일 진입점

모든 상태 전이는 `services/state_machine.py`의 `transition()` 함수만 통과한다. DB 트랜잭션 내에서 `job.status` 업데이트 + `job_events` 기록이 원자적으로 처리된다. 허용되지 않은 전이는 `FSMException`으로 즉시 차단되고 롤백된다.

`SELECT FOR UPDATE` 행 잠금으로 동시에 두 워커가 같은 job을 전이시키는 경쟁 조건을 차단한다.

## 7. 한계 & 개선 방향

### 아직 해결하지 못한 문제

**견적 승인은 여전히 사람이 한다.** 가격과 납기를 클라이언트가 판단해야 하므로, 이 구간은 자동화할 수 없다. 다만 견적 근거(TM 매칭률, 단가 계산 내역)를 투명하게 제공해 결정 속도를 높이는 방향으로 보완할 수 있다.

**QA 판단은 사람이 한다.** 번역 품질 검수는 자동화 기준을 정의하기 어렵다. 현재는 QA 단계에서 리뷰어가 수동으로 승인/반려한다. 장기적으로는 용어집 일치율, 번역 누락 감지 등 보조 지표를 자동 체크할 수 있다.

**배정 점수 모델은 초기값에 의존한다.** 품질 점수와 납기 준수율이 없는 신규 번역가는 점수가 낮게 계산된다. 콜드 스타트 문제를 완화하는 초기값 설정 전략이 필요하다.

## 8. 내가 얻은 인사이트

이 프로젝트를 통해 가장 크게 바뀐 생각:

> "자동화는 기능을 추가하는 것이 아니라, 의사결정을 명문화하는 것이다."

견적 계산 자동화는 수식 하나가 아니다. "TM 매칭률에 따라 얼마나 할인할 것인가"라는 **업계 표준을 코드로 선언**하는 것이다.

번역가 배정 자동화는 알고리즘 하나가 아니다. "어떤 번역가에게 어떤 기준으로 일을 줄 것인가"라는 **조직의 암묵지를 점수 모델로 형식화**하는 것이다.

**AI는 기능이 아니라 흐름에서 가치가 나온다.** 각 단계에서 잘 작동하는 컴포넌트보다, 단계들이 끊김 없이 연결되는 구조가 더 중요하다. 사람이 중간에서 조율하지 않아도 되는 흐름을 설계하는 것 — 그것이 이 시스템의 목표였다.

## 9. 확장 가능성

이 시스템의 핵심 구조는 **"요청 → 자동 분해 → 규칙 기반 처리 → 상태 추적 → 자동 알림"** 이다.

번역 플랫폼 외에도 동일한 구조가 적용되는 영역:

| 도메인 | 자동화 가능한 흐름 |
|--------|-------------------|
| 법률 문서 검토 | 접수 → 유형 분류 → 담당 변호사 배정 → 진행 상태 추적 |
| 디자인 외주 | 의뢰 → 작업 범위 산정 → 프리랜서 매칭 → 납품 |
| 고객 지원 티켓 | 접수 → 카테고리 분류 → 담당자 배정 → 에스컬레이션 |

변하는 것: 도메인 규칙(견적 공식, 배정 기준)
변하지 않는 것: FSM 기반 상태 관리, 비동기 워커, 이벤트 기반 알림 구조

이 설계를 범용 "작업 자동화 프레임워크"로 추상화하면, 도메인만 교체해 다른 워크플로우에 재사용할 수 있다.

## 10. 빠른 시작

### 환경 변수 설정

```bash
cp .env.example .env
# .env 파일을 열어 실제 값 입력
```

### Docker Compose 실행

```bash
docker-compose up -d
```

### 마이그레이션 실행

```bash
docker-compose exec api alembic upgrade head
```

### API 문서 확인

- Swagger UI: `http://localhost:8000/docs`
- ReDoc: `http://localhost:8000/redoc`
